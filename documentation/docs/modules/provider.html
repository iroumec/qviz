9  Provider

The provider module is found in backend/core/provider/. It has two responsibilities. The family of the backend is recognised, and the noise profile of a reference machine is chosen. Two files are used: provider.py and profiles.py.

detect(backend, entangler=None)

The main function of the module. The provider, the entangler and the noise profile of a backend are returned together in one BackendInfo object.

Parameters

Name Type Default Meaning
backend any object required The backend that is injected by Qollab, or a local backend in a test.
entangler "ms" or "zz" or None None The target entangler. When it is None, the entangler is inferred from the backend and from its name.

Returns a BackendInfo object. See the Data model page for its fields.

How the entangler is chosen

The following order is used. The first step that gives an answer is kept.

  1. The parameter. When entangler is given, it is used as it is.
  2. The backend itself. When the backend advertises only one native two-qubit gate, that gate is used. For example, a backend whose operation names contain zz but not ms gives "zz".
  3. The machine family. The family is read from the machine hints: options.noise_model first, and then the name (see below). The helper native_2q_gate of qiskit-ionq turns a hint such as aria-2 into "ms". A hint that contains forte or ideal also gives "zz".
  4. The default. When nothing is found, "ms" is used.

A name that contains ideal is treated as a zz machine, because the ideal reference is paired with the fixed zz entangler.

The IonQ machine family

Every IonQ entry in Qollab is named ionq_simulator, so the name does not say whether the machine is an Aria (MS) or a Forte (ZZ). The family is read from backend.options.noise_model instead, which is aria-2, forte-1, forte-enterprise-1 and so on. The helper native_2q_gate from qiskit-ionq converts that value into ms or zz.

The machine hints are therefore collected from two places, in this order: options.noise_model, then the name. Each hint is tested with native_2q_gate, and the first hit is used. When options.noise_model raises an exception (as it does for AWS and the built-in simulator) or holds a NoiseModel object (as it does for IBM), it is ignored, and the name is used.

How the hardware flag is set

is_hardware is True only for an IonQ backend that is not a simulator. A boolean attribute of the backend is preferred, because it is set by the software development kit itself. The attributes _simulator, _is_simulator, is_simulator and simulator are checked, in this order.

The name is inspected only as a last resort, when no attribute is found. This is deliberate. A name is a weak signal, and it can be misleading. The attribute is always preferred when it exists.

detect_provider(backend)

The family of the backend is found, and one of the five provider names is returned.

Parameter

Name Type Meaning
backend any object The backend to classify.

Returns one of "ionq", "ibm", "aws", "local" or "unknown".

The detection is layered. The reliable signals are checked first, and a structural fallback is used last.

The first signals

Signal Provider
the class module starts with qiskit_ionq, or the name contains ionq ionq
the module is qiskit_ibm_runtime, the name starts with fake_ or ibm_, the class is GenericBackendV2, or the module contains ibm ibm
the module starts with qiskit_braket_provider, or the name contains braket aws
the module, the class or the name contains BasicSimulator, basic_simulator, aer_simulator or AerSimulator local

The structural fallback

When the signals above give no answer, the operation names that the backend advertises are inspected. They are read from target.operation_names, from operation_names, or from configuration().basis_gates.

Operation names that are found Provider
any of gpi, gpi2, ms ionq
ecr ibm
cz, rz and sx together ibm
anything else unknown

Only gpi, gpi2 and ms are treated as IonQ-native here, because zz and rxx also exist as ordinary Qiskit gates and would produce false positives. The Qollab IBM simulators advertise cz, rz and sx together, which is the signal that is used for ibm.

This fallback exists so that a backend with an unusual name, but with a clear gate set, is still classified correctly. An unknown provider is never an error, because the generic translator is used for it.

The noise profiles

The file profiles.py contains three ready-made profiles.

Constant Machine Notes
ARIA IonQ Aria Used for the MS entangler.
FORTE IonQ Forte Used for the ZZ entangler.
IDEAL an ideal machine All fidelities are 1, and all prices are 0.

The numbers are simple estimates that were taken from public IonQ material. They are not a calibrated noise model. They can be replaced before the demo.

profile_for(provider, name, entangler)

The correct profile is chosen for a backend.

Parameters

Name Type Meaning
provider string The provider name. Only "ionq" uses the name of the backend.
name string The best machine hint: options.noise_model when it is a string, and the raw backend name otherwise. For IonQ it is used to find aria, forte or ideal.
entangler "ms" or "zz" The fallback entangler when the name gives no hint.

Returns a NoiseProfile.

The rule. For an IonQ backend, the name is checked first. A name that contains ideal gives the ideal profile, forte gives the Forte profile and aria gives the Aria profile. If the name gives no hint, or if the backend is not IonQ, the reference machine of the entangler is used: Aria for MS and Forte for ZZ. A non-IonQ backend is therefore shown as if it ran on trapped ions, whatever its name is.
